# 出品・最新化の画像取り違え防止（2026-10-27）

旧実装は、同じ秒に準備した商品の管理番号から末尾の識別子を除いた
`legacy_candidate` を画像名に使用していた。保存先が重なり、後の商品は
「ファイルが存在する」だけで先の商品画像を再利用していた。
アップロード側でも同じ名前へ戻していたため、準備側だけの修正では防げない。

## 修正後

- 管理番号全体・ASIN・画像順・元画像URLから画像名を決定する。
  SHA-256の先頭80ビットを小文字Base32で16文字にし、`.jpg` を含め20バイト。
  Cabinetのファイル名長制限内に収める。通常出品・条件無視出品・最新化で共通。
- 準備、送信予定表示、アップロードで同じ関数を使用する。
  既存の共有画像名へ書き戻さず、新しい商品別の名前を使用する。
- 保存済みの旧方式の準備データも、通常実行時に画像の保存先・送信名だけを
  新方式へ移行する。取得元URL、画像順、枚数、出品条件は変えない。
- ダウンロードは毎回取得し、実行ごとの専用フォルダへ保存する。
  出所を確認できない旧ファイルの再利用や、並行処理による上書きを防ぐ。
  元画像取得に失敗した場合は過去の画像へフォールバックせず、その商品の送信を止める。
  ロゴ合成は引き続き元画像を保存したまま別ファイルを作る。
- 新方式の画像アップロード後再開は同じ画像名を利用できる。
  実際にアップロードした画像計画・URLを履歴へ保存するため、旧準備データを
  新方式へ移行して送信した後に失敗した場合も、確認済みの新URLで再開できる。
  旧方式の `--resume-after-image-upload` は一致を保証できないため送信前に止める。
  画像再取得を含む通常実行へ戻す場合も、既存の履歴・重複実行ガードに従う。
  すでに商品登録済みの在庫のみ再開は画像・商品を書き換えず、従来のURLを維持する。

既存商品の画像修復、DB変更、楽天API送信はこのコード配布には含まない。
出品担当PCの `price_system_listing` を更新し、起動済み処理を安全に終了してから
新しい処理を開始する必要がある。QNAPの更新だけでは実行PCへ反映されない。

検証は `tests/test_listing_image_isolation.py`（実際の3組の管理番号、旧保存ファイル、
並行取得、取得失敗、再開、ロゴ合成）と `test_content_refresh_policy.py`。
画像・API応答をローカル生成し、実DBとHTTPへの接続は禁止している。

API仕様: `reference/rakuten_api/spec_pages/07_R-CabinetAPI（CabinetAPI）/08_cabinet.file.insert.md`。
