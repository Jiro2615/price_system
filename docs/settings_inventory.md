## Purpose

This document inventories the current runtime settings and CLI arguments used by the Amazon check workers, Rakuten update workers, and target recalculation flow.

The goal of management feature v1 is:

- keep normal operating values in DB
- keep temporary test and one-shot controls in CLI
- keep secrets in `.env`
- apply settings with this priority:

```text
CLI explicit value
-> DB setting
-> code default
```

This document is design-only. It does not change code or database state.

## Classification Rules

- `store_setting`: store-specific operating policy that should usually live in DB
- `amazon_worker_setting`: Amazon worker normal operating value
- `rakuten_worker_setting`: Rakuten worker normal operating value
- `node_setting`: machine-specific local setting
- `runtime_only`: execution mode or one-shot behavior, not persisted in DB
- `secret_env`: secret or connection credential, stays in `.env`
- `debug_only`: temporary filter, output path, or test aid

- `log_retention_days`

- `api_interval_seconds`
- `verify_wait_seconds`

Store-level operating toggles:

- whether target recalc is enabled for the store

## Naming and Redundancy Issues

### Repeated names with different meanings

- `--limit` means different things in different scripts
- `--sleep` exists for Amazon normal loop timing, but Rakuten uses `--empty-sleep` and `--error-sleep`
- `--output` always means debug/export path and should not be promoted to DB

### Current mismatches

- `start_amazon_workers.ps1` default `PageTimeout` is `15000`, while Python defaults are `60000`
- `amazon_check_worker_loop.py` requires `--worker-id`, but normal launcher use now auto-generates it

### Existing DB settings that must remain the source of truth

Do not duplicate these into new worker configuration tables:

- price calculation policy in `stores`
- price band rules in `price_rules`
- existing inventory cap through `stores.max_stock`

## Management Feature v1

Minimum DB scope:

- `store_settings`
- `worker_nodes`
- `worker_configs`
- `worker_status`

`worker_commands` is intentionally deferred for v1.

### Design Principles

- secrets remain in `.env`
- worker operating defaults move to DB
- CLI explicit values override DB
- DB values override code defaults
- one Rakuten update worker per store for now
- Amazon worker count is node-managed, not store-managed

Delete rules:

- `stores -> worker_configs`: `ON DELETE RESTRICT`

- `worker_type IN ('amazon_check', 'rakuten_update')`
- `desired_state IN ('running', 'stopped')`

- `revision >= 1`
- `settings_json` is `NOT NULL`

- `jsonb_typeof(settings_json) = 'object'`
- `amazon_check` rows: `worker_number` required, `store_id` must be `NULL`
- `rakuten_update` rows: `store_id` required, `worker_number` must be `NULL`

- `amazon_check`
- `rakuten_update`

- `running`
- `stopped`

## Deferred: Batch Job Management

`rakuten_csv_price_update_flow.py` should not be managed by `worker_configs`.

Reason:

- it is not a long-running worker
- it is a one-shot batch job
- it has execution-time parameters that differ from normal worker settings

Future management should add separate single-run job control, for example:

- `job_commands`
- `job_runs`

Expected future job type:

- `rakuten_csv_price_update`

### Expected Web UI capabilities for CSV batch jobs

- preview target count
- generate CSV
- execute bulk CSV update
- show progress
- show success count, failed count, and blocked count
- show error log
- run blocked-product API fallback

### Concurrency rule

When a Rakuten CSV price update job is running for a store:

- the Rakuten price API worker for the same store must not run at the same time
- Amazon checking can continue
- Rakuten inventory updates can generally continue

This means future batch-job control needs a store-scoped exclusion rule at least for:

- `rakuten_csv_price_update`
- `rakuten_update` price step for the same store

### Parameter ownership

CSV batch execution parameters should not be stored in `worker_configs`.

Examples:

- `limit`
- `timeout`
- `settle_wait`

These should be handled as one of:

- explicit job execution parameters
- future job default values

They should not be treated as always-on worker settings.

- worker `enabled`
- Amazon `settings_json`
- Rakuten `settings_json`
- runtime status and heartbeat from `worker_status`

### Keep internal or advanced-only

- `worker_id`
- `pid`
- `revision`
- `project_dir`
- `python_command`
- manual debug filters like `asin`, `manage-number`, `sku`
- all secret env values

## Review Notes

### Good candidates for DB first

- `worker_configs.settings_json`
- `worker_nodes`
- minimal `store_settings` flags

### Keep launcher ini files as temporary compatibility

Until launchers read DB directly, local ini files can remain as a convenience cache, but DB should become the intended system of record.

### Avoid double ownership

- price logic stays in `stores` and `price_rules`
- worker operation values move to `worker_configs`
- secrets stay in `.env`

## updated_at Policy

Management feature v1 should use application-side updates for `updated_at`.

Reason:

- keep the initial migration simple
- avoid introducing triggers before worker write paths are implemented
- make update timing explicit in application code

This applies to:

- `store_settings.updated_at`
- `worker_nodes.updated_at`
- `worker_configs.updated_at`
- `worker_status.updated_at`
